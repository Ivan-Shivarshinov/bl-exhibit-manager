# Участие в разработке

Начните с [карты продукта](docs/ROADMAP.md), [OpenSpec](openspec/README.md) и [инструкции запуска и сборки](docs/DEVELOPMENT.md). Согласованные изменения находятся в `openspec/changes/`, действующее поведение — в `openspec/specs/`.

Для знакомства запустите готовое приложение и нажмите «Открыть учебный комплект». Это вымышленные документы: их можно использовать для воспроизведения ошибок. Панель Word и переводчики необязательны; для преобразования основного DOCX в PDF нужен отдельный конвертер.

## Ошибка или предложение

Создайте issue по шаблону. Для ошибки укажите шаги, ожидаемый и фактический результат. В приложении откройте «Помощь и настройка» → «Показать сводку диагностики» → «Копировать сводку». Просмотрите её перед публикацией.

Не прикладывайте клиентские документы, переписку, имена проектов, папки данных, ключи, сертификаты или полные журналы. Сделайте минимальный вымышленный пример. Сводка не отправляется автоматически.

## Изменения кода

1. Создайте отдельную ветку, сохраните чужие незавершённые изменения.
2. Для нового поведения сначала обновите соответствующие proposal, specs, design и tasks в OpenSpec. Идея в ROADMAP ещё не является принятым требованием.
3. Сохраняйте исходники документов, оформление и существующие ссылки. Word остаётся опциональным; Windows/macOS и Claude/Codex равноправны.
4. Запустите проверки из DEVELOPMENT и пройдите затронутый сценарий от загрузки до результата. Укажите отдельно автоматические, реальные Office и ручные проверки; не выдавайте одну среду за другую.
5. Выполните `openspec validate --all --strict --no-interactive`. В PR кратко опишите проблему, изменение, проверки и оставшиеся ограничения. Проверьте состав новых файлов перед коммитом.

Рабочие материалы и результаты локальных тестов в Git не включаются. Публичные описания релизов содержат только полезные пользователю изменения и инструкции запуска.
