## Context

База — выпущенная v0.4.0. Подачи хранятся независимо; `project.py` управляет документами/назначениями и проверкой готовности, `history.py` — неизменяемыми ZIP, `backup.py` — проверяемыми архивами, `schema.py` — защищёнными миграциями. Библиотеки и связей происхождения пока нет. Состав и статус объёма — proposal.md; ядро и R1–R4 приняты целиком для 0.5.0.

## Goals / Non-Goals

**Goals:** повторное использование проверенного материала с ясным происхождением; самостоятельная подача; предсказуемое обновление без потери местной работы; полный перенос библиотеки.

**Non-Goals:** единая изменяемая ссылка вместо файла подачи, распределённая синхронизация, фоновое изменение Word, работа с данными коллег для тестов. Сравнение показывает различия документов, но не даёт правового заключения и не обещает полноценный redline.

## Decisions

### 1. Пользовательский путь и границы сущностей

Раздел «Библиотеки дел» доступен со стартового экрана и из подачи; обычные «Новая», DOCX/PDF и экспорт сохраняются. При добавлении в подачу контекст целевой подачи явно указан. Не вводить обязательный мастер «сначала создайте дело».

Библиотека — именованный локальный каталог одного дела. Материал — документ с постоянным ID, независимо от Annex 3/12. Версия — неизменяемый снимок содержания и реквизитов. Приложение — копия конкретной версии в подаче со своим ID, номером, папкой, именем и состоянием проверки. В одной подаче допустимы материалы из разных библиотек.

Карточка: название, краткое название, язык, комментарий к версии, дата создания версии и состав частей. Дата документа отличается от даты добавления. В R2 добавляются необязательные дата документа, категория и метки. Не требовать заполнения всех полей ради импорта. Номер приложения принадлежит подаче, а не карточке материала.

### 2. Хранилище и неизменяемость

Контракт реализации 0.5.0: `library.json` (schema 1) содержит ID, имя, ревизию, карточки/упорядоченные ID версий и результаты идемпотентных операций. Неизменяемый `versions/<version_id>.json` содержит schema 1, library/material/version/parent ID, UTC-время, реквизиты, роли `original`/`translation`/`ready`, размеры/SHA-256/страницы и рецепт. Файлы — `blobs/<sha256>.pdf`. Происхождение в приложении хранит точные ID, хеш манифеста и базовый снимок переносимых полей; локальные назначения остаются в документе подачи. Схема подачи 2 применяется через проверенный архив только перед первым добавлением происхождения; простое чтение/восстановление старой подачи сохраняет schema 1. Старое приложение отклоняет schema 2. Предварительный выбор и временные файлы живут отдельно от опубликованных карточек; ответ на повтор определяется записанным результатом операции, а не наличием временного файла.

Отдельный каталог `libraries/<library_id>/` рядом с подачами: манифест библиотеки, материалы и манифесты версий, неизменяемые файлы по SHA-256, служебная staging-зона. Не превращать готовый архив подачи в источник файлов библиотеки. Файлы в существующих подачах не перемещать и не заменять общими ссылками.

Манифест версии содержит ID/родительскую версию, дату, реквизиты, роли файлов, размеры/хеши/число страниц, сведения о подтверждении перевода и рецепт подготовки с фактически применёнными настройками. Оригинал, перевод и готовый PDF — разные роли. Готовый PDF никогда не выдаётся за оригинал.

Публиковать версию только после проверки файлов атомарной сменой манифеста. Применять блокировку записи и сравнение ожидаемой ревизии; два окна с устаревшим состоянием не перезаписывают друг друга. Повтор того же запроса после обрыва не создаёт вторую версию/копию. После перезапуска незавершённая операция не выглядит успешной. Мусор staging не затрагивает подтверждённые файлы.

Файловая модель — источник истины; индекс названий и реквизитов восстанавливается из манифестов. SQLite не вводить ради простого каталога. Полнотекстовый индекс — отдельное будущее решение. При больших списках читать страницу метаданных, не открывать все PDF и не вычислять все хеши заново на каждый поиск.

### 3. Наполнение и повторное использование перевода

Основной вход ядра — сохранение выбранного приложения из подачи. До применения показать состав: оригинал, подтверждённый перевод, готовый PDF (если он действителен), сведения о текущем обозначении. Предложить новый материал либо новую версию выбранного материала; совпавшее название не означает идентичность.

Неподтверждённый перевод не переносить молча как готовый. Можно явно сохранить только оригинал; интерфейс сообщает об исключённом черновике. Подтверждение перевода привязано к конкретному оригиналу/выборке и его хешу. При замене оригинала старый перевод можно сохранить для сравнения, но его применимость нужно подтвердить заново. Не запускать Claude/Codex при сохранении, сравнении или импорте. Если перевод подтверждён для той же части оригинала, повторная генерация и повторная проверка его текста не требуются только из-за нового номера.

R1 добавляет многострочный предварительный список для материалов подачи и прямой загрузки PDF. Для каждого файла пользователь выбирает роль (оригинал или уже готовый PDF); переводы явно привязываются к материалу. Не угадывать пары по имени. Ошибочные строки можно исключить до подтверждения; итоговая выбранная операция применяется целиком либо не применяется.

### 4. Каталог, поиск и просмотр

Поиск ядра: название, краткое название, исходное имя; сортировка по названию/дате версии, переключение старых версий и просмотр оригинала/перевода/готового результата. Запрос без результатов отличается от повреждённого каталога. Предпросмотр грузит выбранные страницы с ограничением памяти. Интерфейс показывает ход длительной операции, отмену до публикации и результат рядом с действием; обычные операции не порождают alert.

R2: пользовательские категории/метки, дата документа, фильтры языка/перевода. Проверка точного дубликата сравнивает хеши частей; равный оригинал и разный перевод — не одинаковая версия. Варианты: использовать найденный материал, создать версию выбранного или сохранить отдельный материал. Никакого автоматического удаления или объединения. Сходство текста без совпадения байтов не объявляется дубликатом.

### 5. Импорт в подачу

Два режима: (a) оригинал + подтверждённый перевод + пригодные настройки для новой подготовки; (b) готовый PDF без обработки. Для (b) показывать прежнее обозначение: смена имени/номера не меняет штамп внутри PDF. Для (a) переносить эффективные значения, не ссылки на настройки исходной подачи; назначения целевой подачи пользователь видит до записи.

Предварительный просмотр фиксирует конкретные library/material/version ID, манифест и ожидаемую ревизию целевой подачи. Проверять полный идентификатор и итоговый относительный путь с учётом Unicode/case и ограничений Windows/macOS. Не занимать номер молча. R1 предлагает свободные последовательные номера и папку для выбранного набора, используя существующие правила массовых назначений.

Файлы копируются в собственное хранилище подачи, документ получает новый ID и `provenance` со снимком источника. Project.json публикуется после завершения копирования; сбой не оставляет частично добавленные приложения. Обнаруженный изменившийся проект требует обновить предварительный список. Подготовка и готовность вычисляются в целевой подаче: перенос старого approved-хеша недопустим. Готовый PDF сохраняется побайтово.

### 6. Сравнение версий

Показать выбранные версии, дату/комментарий и таблицу частей: оригинал/перевод/готовый PDF/настройки/название, изменён или нет, число страниц до и после. Хеш — внутреннее доказательство, не основное объяснение пользователю. Две версии выбранной части открываются рядом; у каждой свой номер страницы, масштаб и понятное имя версии. На узком экране — переключение «до/после» с сохранением позиции. Добавление/удаление страниц не выдаётся за автоматическое смысловое сопоставление.

Автоматическая подсветка текстовых/визуальных изменений и OCR не нужны для первого сравнения: у скана доступен тот же просмотр. Отсутствие извлечённого текста не означает отсутствие изменений. Если часть повреждена, сравнение сообщает это и не показывает «одинаково».

### 7. Явное обновление и местные изменения

Подача хранит точную исходную версию и базовый снимок полей. Новая версия только порождает уведомление. Открытие/обновление каталога не меняет подачу. Обновлять можно выбранную версию, в том числе прежнюю, явно; слово «новая» обозначает порядок сохранения, а не юридическую актуальность документа.

До применения показать изменённые части, местные изменения и какие проверки сбросятся. Номер, папка, выходное имя, ID приложения и назначенные ему ссылки сохраняются. Изменённые в подаче название/выбор страниц/перевод/оформление нельзя молча затереть: пользователь выбирает, что принять, либо отменяет. Если источник изменился, старые диапазоны страниц проверяются заново; вне диапазона — понятный конфликт, а не обрезание. Смена оригинала снимает применимость прежнего перевода; смена одного названия не требует повторного AI-перевода.

Перед применением сделать проверяемый локальный снимок подачи существующим механизмом архива. На ошибке остаётся прежняя версия; путь к снимку доступен в результате операции. Это возможность восстановления, а не новый общий журнал undo. DOCX на диске не переписывается библиотекой: изменённые названия проходят существующую проверку ссылок/явное применение в панели. Не сбрасывать подтверждения незатронутых приложений. Прежние ZIP всегда неизменны.

R3 строит восстанавливаемую справку по происхождению документов локальных подач, а не авторитетный сетевой список. Показывать имя подачи, номер, точную версию, локальное изменение и доступность новой версии; переход открывает нужную подачу. Отдельно сообщать о недоступных/повреждённых проектах. R4 хранит флаг скрытия в карточке материала, не удаляя версии или файлы.

### 8. Архивы, конфликты и перенос

Отдельный тип архива `library`, с версией формата, манифестом, всеми версиями и обязательными файлами. Проверки по модели backup.py: ограничение размера/числа записей, потоковые хеши, allowlist, запрет traversal/symlink/дублей/абсолютных путей и секретов. Предел первого формата — 8 ГБ распакованных данных и 20 000 записей; превышение объяснять до выдачи архива. Индексы/кеш/учётные данные/пути компьютера не переносить.

На новом компьютере сохранить library/material/version ID после полной проверки. При конфликте существующую библиотеку не перезаписывать: отмена либо независимая копия с новыми ID библиотеки и материалов и переназначенными внутренними связями; автоматического слияния нет. Такая копия не становится источником обновлений чужой подачи автоматически. Восстановленная с исходными ID библиотека соответствует provenance только при совпадении хеша сохранённой версии; совпадение имени/ID без содержимого недостаточно.

Архив подачи содержит все её файлы и provenance как справку, но не всю библиотеку. При отсутствии библиотеки доступны редактирование и экспорт; новые версии недоступны с объяснением. Если библиотеку восстановили позже с совместимой идентичностью, проверка новых версий становится доступна без перезаписи подачи.

### 9. Миграции, нагрузка и приёмка

Перед реализацией определить минимальную версию схемы, чтобы старое приложение не отбросило provenance при редактировании. Если нужна миграция project.json — использовать защиту schema.py с проверенным архивом до изменения. Старые ZIP v0.3/v0.4 должны восстанавливаться без обязательной библиотеки. Новые неподдерживаемые схемы читаются только после обновления, без записи старым приложением. Откат версии приложения — через сохранённый архив, а не попытку открыть новые данные старым кодом.

Проверять каждый вертикальный срез сразу. Искусственный сквозной набор: два дела, две подачи, 20 материалов; один и тот же материал имеет два номера; перевод v2 обновляет только одну подачу. Отдельно нагрузка: 1000 карточек/3000 версий, массовый набор 100 PDF (R1), большой скан. Целевые бюджеты на зафиксированных Windows/Mac runner: тёплый поиск метаданных p95 <= 1 с, первая страница каталога <= 2 с, видимая обратная связь на действие <= 300 мс; измерять условия и фактические результаты, не обещать скорость любого пользовательского диска. Хеширование/архивы потоковые, прогресс не требует загрузки всего PDF в память.

Проверки готовых пакетов Windows x64/Mac Intel/ARM и взаимный обмен архивами обязательны для изменённого сценария. Внедрение библиотеки не требует повторить всю установку панели. Если затронуты Office.js или обновление ссылок после изменения названия, провести адресную проверку в настоящем Word, честно отделив остальные среды. Обратная связь коллег не заменяет проверки и не является формальным ожиданием.

## Risks / Trade-offs

- Больше копий на диске → размеры видны до импорта/архива; независимость подачи важнее глобальной дедупликации.
- Старый штамп/несоответствующий перевод → явный режим готового PDF, привязка подтверждения перевода к оригиналу, повторная проверка только затронутого.
- Потеря местных правок → сравнение с базой происхождения, явный выбор, снимок до обновления.
- Прерывание/конкурирующая вкладка → staging, проверка ревизии и идемпотентность.
- Сложность интерфейса → необязательный каталог, один явный следующий шаг; массовые операции через предварительный список.
- Расширение объёма → R1–R4 обязательны для 0.5.0; перечень приложений/OCR/облако не становятся незаметными условиями выпуска библиотеки.

## Migration Plan

1. Закрепить форматы и искусственные примеры; проверить открытие v0.4 без миграций до команды изменения.
2. Реализовать каталог и сохранение одного материала, затем сразу независимый импорт и экспорт подачи.
3. Добавить версии/сравнение и явное обновление с проверкой сохранности двух подач.
4. Реализовать архив библиотеки и перенос; затем все согласованные R1–R4.
5. Нативные пакеты, адресные проверки, инструкция и OpenSpec. Архивировать change только после выполнения принятого объёма; фактический релиз отмечать отдельно.
