## Context

В кандидате 0.4.0 работают учебный комплект, диагностика и подготовка файлов Word. Ручная проверка 5 октября выявила несоответствие цели: пользователю приходится самому устанавливать сертификат, создавать общую папку, подключать каталог и манифест. Кроме того, Python принимал сертификат из промежуточного хранилища Windows, хотя браузер его отклонял; это исправлено. Закрытие change отменено.

## Goals / Non-Goals

**Goals:** короткий обычный первый запуск и отдельное удобное подключение опциональной панели; проверяемая готовность каждого шага; повторяемая настройка без потери документов и чужой конфигурации.

**Non-Goals:** обязательный Word, установка Office/CLI, скрытое изменение доверия, обход политик организации, управление мышью пользователя, автоматическое закрытие Word, публикация в магазине/внешний хостинг без отдельного решения.

## Decisions

- Основная работа доступна сразу. Диагностика показывается по нужной операции; Word настраивается отдельно, раскрываемая техническая инструкция остаётся резервным средством.
- Повторно открыть задачи подключения и приёмки. Прежние нативные тесты доказывают запуск, обработку документов и TLS с заданным CA, а не самостоятельную установку панели.
- Выбран локальный экспериментальный sideload для пилота (решение пользователя 5 октября). На Windows используется регистрация GUID → путь XML в HKCU `Software\\Microsoft\\Office\\16.0\\WEF\\Developer`, как в официальном `office-addin-dev-settings`; на Mac — собственный XML в `wef` Word. Не включать отладчик, не менять политики, не создавать SMB. Сравнение вариантов — `docs/WORD-INSTALLATION-OPTIONS.md`; Marketplace не выбран.
- Команда подключения объясняет доверие к собственному localhost-сертификату, регистрацию и открытие нового учебного DOCX. Windows: только Root текущего пользователя. Mac: доверие SSL к localhost в связке пользователя через системный `security`, с необходимым запросом ОС; не менять authorizationdb. Для проверки доверия Mac использовать системный `security verify-cert`, а затем проверять TLS-соединение; Python OpenSSL сам по себе не подтверждает Keychain trust.
- До изменений фиксировать владение объектами; уже существующее доверие сохраняется. Не заменять чужую запись с тем же GUID/именем файла. Отмена и ошибка откатывают только объекты, созданные текущей попыткой. Отдельная команда удаления затрагивает только собственную регистрацию и собственное установленное доверие; конфигурация, ключ, документы и проекты сохраняются.
- Новый учебный DOCX содержит собственную ссылку webextension на зарегистрированный GUID (`developer`/`Registry`) и видимую панель, как sideload-документ Microsoft. Каждый запуск создаёт новый файл, не меняет открытый пользовательский документ и не закрывает Word. Если Office требует перезапуска, пользователь сохраняет документы и перезапускает Word сам.
- Целевой путь: «Подключить панель» → объяснение системных изменений и необходимых подтверждений → открытие панели в Word. Приложение отвечает за технические файлы и регистрацию. Сертификат уникален для компьютера; обновление не заменяет его. Установка выполняется только по явной команде, повтор идемпотентен; удаление касается только созданных приложением объектов.
- Состояния различаются: подготовка, ожидание системного подтверждения, требуется действие в Word, подключено, ошибка. «Подключено» требует подтверждения от панели внутри Word, а не HTTP 200 или наличия файла. В браузере показывается инструкция открыть Word, не ложная просьба обновить Office.
- Отмена/ошибка не блокирует основной HTTP-процесс. Не менять политики Office, не очищать общий кеш, не закрывать окна, не удалять чужие каталоги или сертификаты. Частичная установка должна допускать повтор без дублирования объектов; откат затрагивает лишь собственные изменения.
- Windows и Mac имеют отдельные результаты. Нельзя подменять незаконченный путь на одной ОС длинной инструкцией и закрывать весь этап. Ограничение, которое требует изменения согласованного объёма, выносится как конкретное решение, а не скрывается в release notes.
- Пользователь не выбирает порт в обычном пути. При новой подготовке приложение выбирает свободный локальный порт; действующая конфигурация сохраняется. Явный порт остаётся технической настройкой для диагностики.
- Панель сообщает о готовности только после `Office.onReady` для Word и проверки WordApi 1.5. Короткая сессия в памяти процесса обновляется панелью; закрытие и истечение сессии снимают состояние подключения. Обычное открытие страницы и HTTP health не создают сессию. Статус HTTPS хранится отдельно и не подменяет состояние панели. Проверка реального Word runtime перед регистрацией не читает текст документа.
- Совместимость проверяется по API, а не названию подписки. WordApi 1.5 документирован для Microsoft 365, совместимых розничных бессрочных редакций и Office 2024/LTSC; поддержка установки проверяется отдельно. Не предлагать купить Microsoft 365 пользователю совместимой редакции.
- Использовать доступные виртуальные macOS Intel/ARM runners для нативных пакетов, локального сервера и автоматического сценария. Для доказательства Office.js нужна среда с настоящим установленным и активированным Word; имитация host в браузере явно учитывается отдельно. В доступной конфигурации CI есть macOS runners с LibreOffice, self-hosted runners отсутствуют; Mac пользователя не предполагается.

## Проверенные источники и ограничение решения

Проверено 5 октября 2026:

- [Microsoft: network share](https://learn.microsoft.com/en-us/office/dev/add-ins/testing/create-a-network-shared-folder-catalog-for-task-pane-and-content-add-ins) — способ тестирования Windows, не production deployment. Он не является целевым самостоятельным подключением лишь потому, что его удалось автоматизировать.
- [Microsoft: sideload на Mac](https://learn.microsoft.com/en-us/office/dev/add-ins/testing/sideload-an-office-add-in-on-mac) — локальное тестирование с файлом в wef, не публикация для пользователей.
- [Microsoft: распространение надстроек](https://learn.microsoft.com/en-us/office/dev/add-ins/publish/publish) — публичное распространение через Marketplace и организационное через Microsoft 365 admin center. Эти варианты требуют отдельного рассмотрения; доступ к tenant, магазин и хостинг сейчас не предполагаются.

Механизм выбран для пилота; его прототип и реальные границы ещё требуют проверки. Официальный исходный код: [Windows registration](https://github.com/OfficeDev/Office-Addin-Scripts/blob/master/packages/office-addin-dev-settings/src/dev-settings-windows.ts), [Mac registration](https://github.com/OfficeDev/Office-Addin-Scripts/blob/master/packages/office-addin-dev-settings/src/dev-settings-mac.ts), [sideload document](https://github.com/OfficeDev/Office-Addin-Scripts/blob/master/packages/office-addin-dev-settings/src/sideload.ts). Эти механизмы не переименовываются в production deployment.

## Risks / Trade-offs

- Корпоративные ограничения или неподдерживаемая версия Office → объяснить недоступность и сохранить обычную загрузку DOCX; не обходить ограничения.
- Изменение доверия → явное согласие на конкретный локальный сертификат и проверка фактического доверия; не выключать TLS.
- Тестовое подключение ошибочно объявлено готовым продуктом → отдельно фиксировать назначение механизма, путь пользователя и границы подтверждения.

## Migration Plan

При замене собственного TLS listener ожидание завершения не удерживает SETUP_LOCK: незавершённая диагностика может читать настройки. Для HTTPS ограничено graceful shutdown до двух секунд, чтобы открытая панель и незавершённый запрос не блокировали смену сертификата. Проверка реальным долгим HTTPS-запросом подтверждает остановку и ответ нового listener; обычный HTTP сервер не перезапускается.

Проверка восстановления 8 октября воспроизвела потерю повторного импорта и на отдельном новом учебном сертификате: первое добавление в пользовательский ROOT сохраняется, после подтверждённого удаления новое добавление того же DER возвращает успех, но остаётся только в открытом хранилище. В защищённом списке Windows сохраняется его отпечаток. Подмена провайдера, принудительные флаги, изменение ProtectedRoots и политик не используются. При таком результате установка Windows однократно выпускает новый собственный localhost-сертификат, сохраняет прежние файлы сертификата/ключа и порт, обновляет собственный HTTPS listener, затем выполняет обычное защищённое добавление и проверку точного нового доверия. Согласие системы не обходится; отказ/отмена остаются доступны. Нет автоматического обновления сертификата поставщика или уже действующего доверия; второй неподтверждённый импорт заканчивается ошибкой, без цикла перевыпуска. Смена конфигурации и владения сохраняется согласованно для повторного запуска; прежняя регистрация и документы сохраняются.

Исправление по проверке 8 октября: certutil завершил повторное добавление успешно на уровне команды, но сертификат не появился в ROOT; подробный вывод не был сохранён, организационная политика не доказана. Добавление Windows переводится на `CertAddEncodedCertificateToStore` через защищённый системный провайдер CURRENT_USER, с полным DER и ADD_NEW. Чужие объекты не заменяются, принудительные/тихие флаги и изменение политики не используются. Системный запрос выполняется в отдельном процессе готового приложения: таймаут/отмена завершают только этот процесс, затем установка проверяет/откатывает своё доверие. Временный результат содержит только факт добавления или безопасный код ошибки Windows, не документы, ключи или сырой вывод. Успех команды без точного сертификата в ROOT не позволяет перейти к регистрации/открытию Word. Административный домен остаётся исключительно проверкой одноразовых CI-машин.

Исправление по аудиту 7 октября: отдельно воспроизвести проверку HTTPS и снятие собственного доверия внутри готового Windows-пакета. Системные инструменты запускаются с очищенным окружением загрузки библиотек PyInstaller. Частичное удаление сразу снимает installed и прежний кеш доверия; недоступность системной операции не подменяется сообщением о несуществующем запросе подтверждения. Подсказки выводятся по текущему состоянию панели и выбранной подачи; открытие Word заранее обозначено как новый учебный документ.

Прежняя регистрация той же локальной панели распознаётся по ID, имени и localhost SourceLocation манифеста. До установки показывается «Обновить подключение» с отдельным объяснением переключения Word на это приложение. Согласие привязано к снимку обнаруженной регистрации; изменение записи после подтверждения требует новой попытки. До записи сохраняется исходное значение Windows или содержимое XML Mac. Ошибка, отмена и удаление восстанавливают снимок, только если запись всё ещё принадлежит текущей попытке; более поздние чужие изменения не затираются. Неизвестные записи не заменяются. Прежние сертификаты, проекты и файлы другой версии не меняются.

Последнее состояние установки записывается отдельно от владения системными объектами. После перезапуска сохраняются ошибка/отмена; незавершённая операция показывается как прерванная с возможностью повтора. Диагностика читает действующую регистрацию даже без локального файла установки. HTTPS и ожидание Word показываются отдельно; при незавершённой установке следующий шаг — завершить настройку, а не открыть панель. Локальные снимки и сообщения с путями не попадают в копируемую сводку.

Сохранить прежние проекты, сертификаты и действующее подключение. Сначала подтвердить механизм, затем реализовать платформенную настройку и UI, обновить пользовательскую инструкцию и пересобрать пакеты. Отдельно проверить чистую установку, обновление, отмену и повтор. Не возвращать PR из draft и не архивировать change по одному лишь CI; выпуск отмечается отдельно после закрытия критериев.

### Отключение собственного доверия на macOS

При перевыпуске сертификата очищается прежняя сессия панели. Если Windows Word уже запущен, приложение сохраняет состояние `word_restart_required` и предлагает сохранить документы, закрыть все окна Word и нажать открытие нового учебного документа. Read-only проверка процесса WINWORD через tasklist не читает документы и не завершает процесс. Открытие до закрытия Word возвращает тот же понятный следующий шаг. Ответ действующей панели снимает ожидание; состояние сохраняется между запусками приложения. Это учитывает проверенный кеш доверия открытого Word: перезапуск одной панели после смены сертификата недостаточен.

На Windows снятие собственного доверия выполняется через системный CryptoAPI (`CertOpenStore` SYSTEM_W, CURRENT_USER, OPEN_EXISTING; `CertDeleteCertificateFromStore`), после согласия приложения и проверки владения. Сравнивается полный DER сертификата, не имя или шаблон поиска. Это устраняет зависимость удаления от зависающего certutil; политики и чужие сертификаты не меняются. Ошибка Windows возвращается с кодом и возможностью повтора. Основание: [Microsoft CertOpenStore](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certopenstore), [Microsoft CertDeleteCertificateFromStore](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certdeletecertificatefromstore).

`security remove-trusted-cert` зависает в современных headless macOS средах; изменение общих authorizationdb правил не является решением для приложения. При удалении/откате приложение заменяет только своё SSL/localhost правило для собственного сертификата на `deny` и проверяет, что системное SSL-доверие снято. Сертификат и ключ сохраняются для явного повторного подключения; повтор заменяет это собственное правило. Чужое доверие не изменяется. Windows удаляет только собственный отпечаток из ROOT текущего пользователя. Основание: [Apple security CLI](https://github.com/apple-oss-distributions/Security/blob/main/SecurityTool/macOS/security.c), [случай runner](https://github.com/actions/runner-images/issues/12116).
