# Design

## Context

Мотивация и границы — [proposal](proposal.md), пользовательский контракт — [submission-index](specs/submission-index/spec.md). Исходная база — выпущенная 0.5.1, не текущий устаревший main. Подготовительные действия и доказательства — [аудит](../../../docs/RELEASE-READINESS-0.6.0.md).

Сейчас `Store.export()` валидирует проект, обходит `p.documents`, готовит приложения и записывает их в ZIP, добавляет основной DOCX/PDF при его наличии, затем вызывает `history.save_export()`. PDF приложения может отличаться по числу страниц от исходника. Проектные схемы 1/2 и архивы проверяются строго; простое добавление неизвестного поля недостаточно для совместимости. История хранит собственный состав и контрольные суммы.

## Goals / Non-Goals

**Goals:** один состав для предпросмотра, генераторов и ZIP; повторное использование существующей подготовки PDF; переносимые ссылки; ограниченная и проверяемая миграция.

**Non-Goals:** универсальный редактор таблиц, повторный рендер пользовательских PDF, изменение модели библиотек, новая система фоновых работ для всего приложения, переработка основного Word. Существующий экспорт без перечня получает только необходимые изменения общего кода с регрессионной проверкой.

## Decisions

### 1. Подготовка базы — отдельная фаза до функциональности

Перенести выпущенную линию в main без force push, проверить диффы перекрывающихся PR. Воспроизвести сбой создания библиотеки при контролируемой задержке начального списка/каталога. По отчёту известны пустое поле и отсутствие POST, но не доказано, виноват ли React или автоматизация. Исправление определяется воспроизведением; автоматический повтор теста не считается решением.

Сверить и синхронизировать три старых changes. Для `word-authoring` условные наблюдения Word/Mac отделить от принятых обязательств; пользовательские подтверждения не заменять собственной невозможностью воспроизвести их. Архивировать только после синхронизации и проверки доказательств. Альтернатива «оставить старый main и добавить ещё одну самостоятельную линию» увеличивает расхождение выпусков и отклонена.

### 2. Ограниченная конфигурация проекта

Поле `submission_index`: `enabled`, `language` (`ru`/`en`), `title`, `formats` (непустое подмножество docx/pdf при включении), `columns` (pages/path; identifier/title обязательны), `order` (identifier/project/folder). Новые и старые проекты по умолчанию без перечня. При первом включении: оба формата, pages включено, path выключено, порядок identifier. Заголовок по умолчанию «Перечень приложений» / «List of Exhibits», максимум 200 символов; выбранный пользовательский заголовок не переписывается сменой языка. Неизвестные значения, управляющие символы и некорректные типы отклоняются до записи.

Служебные подписи RU/EN выбираются отдельно от содержимого: имена материалов не переводятся. Нет свободного HTML, шаблонов или редактируемых строк перечня: исправления вносятся в карточки документов. Альтернатива отдельной вручную редактируемой таблицы создаёт второй источник истины.

### 3. Миграция только при сохранении настройки

Схема 3, переход 2→3 через имеющийся механизм проверенного резервного архива; для схемы 1 — цепочка 1→2→3. Открытие или несохранённый предпросмотр не обновляют проект. После отключения перечня схема 3 сохраняется. Старое приложение отвергает формат 3 вместо тихого игнорирования настроек.

Расширить строгую валидацию, импорт/экспорт архивов и все места, где текущий код предполагает только схемы 1/2. Библиотечная схема не меняется; импорт и обновление материала обязаны сохранять настройки перечня. Новый проект без перечня остаётся на прежнем формате до действия пользователя. Альтернатива «просто добавить поле в schema 2» опасна для старых архиваторов и сохранения через 0.5.1.

### 4. Единый снимок состава

Новый модуль (например, `submission_index.py`) получает неизменяемый снимок настроек и документов: ID, итоговое обозначение, полное название, окончательный safe_path, отпечатки исходников/перевода/выборок/оформления, режим готового PDF, исходный порядковый индекс. Естественный порядок реализовать общим Python-компаратором с фиксированной нормализацией; не полагаться на локаль ОС. Порядок project соответствует сохранённому `p.documents`, а не временному фильтру списка в браузере. Равные ключи упорядочиваются по исходному индексу.

Подготовить PDF каждого приложения один раз для данной сборки; страницы считать по этим точным байтам. Для больших составов допустим временный каталог на той же локальной машине с явной очисткой и пределами; не сохранять полную дополнительную копию пользовательского проекта. Снимок и перечень не содержат абсолютных путей/ID библиотек для получателя. Основной документ и файл перечня не участвуют в сумме страниц приложений.

Отпечаток предпросмотра учитывает настройки, окончательные пути/названия/порядок и все данные, влияющие на PDF. Для выдачи также проверяются актуальные ограничения основного документа и сопоставления. Смена одного заголовка перечня не инвалидирует подготовку приложений или кеш основного PDF. При изменении проекта в другом окне — отказ устаревшего плана. Долгая подготовка выполняется вне глобальной блокировки, публикация — после повторной проверки актуальности в согласованной секции.

Альтернатива считать страницы по метаданным исходника даёт неверные значения для перевода и фрагментов; повторно готовить PDF после предпросмотра без проверки отпечатка также недопустимо.

### 5. Два генератора, общая модель строк

DOCX — python-docx и относительные OOXML hyperlink relationships. PDF — ReportLab, затем проверка/установка относительных GoToR-ссылок средствами pypdf. Не пропускать созданный перечень через внешний Office: для него нет причины вводить зависимость от конвертера. Общая модель строк определяет содержимое, но пагинация двух форматов может различаться.

Формат A4, читаемый фиксированный стиль, повторяемая шапка и номер страницы самого перечня; не создавать сквозную пагинацию подачи. Использовать существующий лицензированный шрифт, покрывающий кириллицу/латиницу. Проверять неподдерживаемые символы до выдачи PDF. Переносить длинные имена/пути, экранировать литералы, разбивать очень большие строки или выдавать явный ограниченный отказ. Области ссылок строятся по фактическим строкам текста, не по высоте всей таблицы. DOCX остаётся таблицей, а не картинкой.

### 6. Файлы, пути и целостность

Имена в корне: `Submission/Exhibit index.docx`, `Submission/Exhibit index.pdf`. Резервировать только реально выбранные форматы; конфликт проверять теми же правилами Unicode/регистра/файл-против-каталога, что приложения. Предлагать пользователю сменить путь конфликтующего приложения, не переименовывать его молча. Названия с `%`, `#`, апострофами и Unicode обрабатывать по формату ссылки, без универсального двойного URL-кодирования.

Для локальных DOCX-гиперссылок сохранять Unicode в относительном IRI, экранируя ASCII-разделители URI однократно (`#` → `%23`, буквальное `%23` → `%2523`). PDF Filespec хранит исходное имя файла в `/F` и `/UF`, без URI-кодирования и без расходящихся платформенных альтернатив. Сверка декодированных целей недостаточна: отдельно проверять представление DOCX и чтение PDF независимым движком. Приёмка нажатий в конкретном Word/PDF-просмотрщике остаётся отдельным доказательством.

Проверить каждую цель относительно корня Submission, запретить выход наружу, localhost и абсолютные файловые пути. PDF-приложения, включая формы/подписи, не изменять ради индексации. Перечень не становится библиотечным материалом.

После сборки сверить: ID строк ↔ окончательные пути PDF ↔ число страниц ↔ ссылки обоих форматов. Валидация проекта не ослабляется. Ошибка на любой стадии не создаёт успешной записи истории и не отдаёт частичный ZIP. Готовые байты перечня попадают в историю как отдельные виды файлов; diff истории показывает изменение перечня, не смешивая его с материалом дела. Состав старых записей читается без обязательных новых полей, существующие ZIP не переписываются.

### 7. API и интерфейс

Предлагаемые маршруты: GET/PATCH `/api/projects/{pid}/submission-index` для настроек, POST `.../preview` для расчёта строк и получения `preview_token`. Реализация может использовать текущий механизм операций при необходимости отмены/прогресса, не создавать параллельный менеджер задач. Экспорт принимает ожидаемый отпечаток/токен при включённом перечне; старый запрос экспорта работает для выключенного перечня. Токен не является разрешением обойти проверки проекта.

В «Проверка и экспорт»: переключатель «Добавить перечень приложений» → настройки → «Обновить перечень» → таблица → существующая «Собрать подачу · ZIP». При расчёте видны состояние/ошибка, кнопка повторного запуска недоступна; отдельные alert для успеха не нужны. После правок видна отметка «Перечень нужно обновить». Перед первым сохранением объяснить сохранение резервной копии и ограничение возврата к старой версии.

Предпросмотр — данные в таблице, а не скачивание отдельного документа с неработающими вне комплекта ссылками. При длинном перечне допустима пагинация/виртуализация таблицы, но показан полный счётчик и каждый документ доступен для проверки. Проверить 1440/760/390 px, клавиатуру и доступность состояния операции.

### 8. Проверки и доказательства

- Контрактные тесты настроек, natural sort, состава и всех отрицательных сценариев спецификации; без реальных документов коллег.
- Парсинг DOCX/PDF: полный текст, порядок, страницы, relative targets, кликабельные области, существование файлов в ZIP; побайтовое сравнение готовых PDF и исходников.
- Сквозные HTTP/UI: включение → предпросмотр → экспорт → перенос → новый экспорт → прежняя история → архив/восстановление копии без библиотеки. Контролируемая правка из второго окна и отказ записи.
- Реальная визуальная проверка созданных DOCX/PDF на искусственных примерах: длинные строки, русский/английский текст, несколько страниц и соседние ссылки. Генерация тестируется без Office; открытие документов в доступных Word/LibreOffice и просмотрщике — отдельное доказательство, не новая runtime-зависимость.
- Нативные пакеты Windows x64/Mac Intel/Mac ARM; обновление от 0.5.1 и архивы старых форматов, взаимный перенос. Настоящая панель Word не меняется и повторной общей приёмки не требует.
- Нагрузка: 100 готовых PDF в полном пакетном сценарии и 500 синтетических строк для генераторов/предпросмотра; записать время, память и временное место, проверить отсутствие потерь/обрезки и лишних повторных конвертаций. Это проверочные объёмы, не новые пределы продукта.

## Risks / Trade-offs

- Повторный отказ UI-теста может быть дефектом приложения → детерминированно воспроизвести задержку и сохранение ввода до объявления причины.
- Миграция затрагивает библиотечные сценарии → schema 3 тестировать вместе с импортом, обновлением, восстановлением копии и ошибкой резервного архива.
- Внешние относительные ссылки поддерживаются просмотрщиками по-разному → проверять структуру целей и реальные переходы в доступных поддерживаемых программах; ограничения просмотрщика описывать конкретно.
- Прямая генерация двух форматов даёт разную пагинацию → контракт сравнивает строки и ссылки, а не номер страницы самого перечня.
- Большие таблицы/длинные значения → ограниченные затраты, перенос/разбиение и явный отказ вместо обрезки; очистка временных файлов при успехе и ошибке.
- Рост объёма релиза → единый PDF-том, OCR и произвольный редактор перечня не входят в задачи.

## Migration Plan

1. Выполнить фазу 0; новая разработка начинается от актуальной единой базы.
2. Добавить поддержку чтения/валидации schema 3 и безопасный переход; настройки по умолчанию выключены. Старые архивы не переписывать.
3. Реализовать состав, генераторы, API/UI и включение в ZIP/историю; до окончания проверок не повышать публичный релиз.
4. Пройти матрицу приёмки и собрать 0.6.0. Сохранить прежние пакеты/теги 0.5.1; возврат проекта после миграции — через проверенный архив до преобразования.
5. Синхронизировать требования и архивировать change только по доказательствам. Публикация релиза — отдельное действие по указанию пользователя.
