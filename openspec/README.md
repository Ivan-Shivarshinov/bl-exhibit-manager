# OpenSpec проекта

OpenSpec 1.8.0, стандартная схема `spec-driven`. Цель продукта и очередность — в [ROADMAP](../docs/ROADMAP.md).

## Где что хранится

- `specs/` — проверяемые требования к принятому базовому продукту. Начальная база восстановлена по коду **v0.1.3-rc.5**, а не только по текущей ветке Word. Это не заявление о проверке каждого документа и каждой среды.
- `changes/` — незавершённые изменения: предложение, требования, решение и список задач. Галочка задачи означает указанную выполненную работу, не автоматический выпуск функции.
- `changes/archive/` — только завершённые изменения после проверки и синхронизации требований. Не создавать задним числом фиктивные архивы прежних релизов.
- [ROADMAP](../docs/ROADMAP.md) — карта продукта, состояние возможностей и кандидаты следующих этапов.
- [WORKSTATE](../docs/WORKSTATE.md) — короткая передача локального контекста: ветка, незавершённое, проверки, пути. Не вторая спецификация и не журнал переписки.

Первоначальные спецификации намеренно покрывают основные пользовательские договорённости, а не каждую функцию кода. Расширять их при изменении соответствующего поведения. Детальные инструкции и результаты проверок остаются в `docs/`, `tests/`, `scripts/`; частные материалы — вне Git.

Ожидание формального отчёта не является условием следующего этапа; отсутствие замечаний не превращается в отметку о пройденном тесте. Не переносить подтверждение на неуказанную ОС/версию или неизвестный сценарий.

## Обычная работа

1. Прочитать `AGENTS.md`, ROADMAP, нужную спецификацию и активное изменение; проверить Git.
2. Для нового поведения создать изменение и записать сценарии до реализации. Для уже согласованного объёма продолжать работу без повторного согласования того же решения. Новые продуктовые идеи не считать утверждёнными.
3. Реализовать, проверять затронутый путь целиком, отмечать задачи с доказательствами и ограничениями среды.
4. Запустить `openspec validate --all --strict --no-interactive`. Эта команда проверяет структуру требований, а не работоспособность приложения.
5. После выполнения критериев синхронизировать спецификации и архивировать изменение. Отдельно отметить выпуск и версию в ROADMAP.

Точечное исправление внутри действующего требования можно связать с существующим change или сделать с регрессионной проверкой без нового набора документов. Опечатки и внутренний рефакторинг не требуют выдуманных продуктовых требований.

## Команды

```sh
npm install -g @fission-ai/openspec@1.8.0
openspec init --tools codex,claude --profile core --no-animation
openspec list
openspec list --specs
openspec status --change optional-word-authoring
openspec validate --all --strict --no-interactive
```

На Windows при ограничении PowerShell использовать `openspec.cmd`. OpenSpec нужен только для разработки. Устанавливать его пользователям приложения не требуется. CI использует ту же закреплённую версию; диагностика OpenSpec не отправляет рабочие документы.

Команды Codex доступны как навыки `openspec-propose`, `openspec-apply-change`, `openspec-archive-change`; Claude — `/opsx:propose`, `/opsx:apply`, `/opsx:archive`. После начальной настройки может понадобиться новая сессия агента. Приоритет имеют текущие указания пользователя и `AGENTS.md`; шаблон навыка не отменяет уже данное разрешение работать.

Официальное руководство: [OpenSpec в существующем проекте](https://github.com/Fission-AI/OpenSpec/blob/main/docs/existing-projects.md).
