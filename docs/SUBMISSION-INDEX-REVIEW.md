## Блокирующие замечания реальной проверки Windows

Среда: Microsoft Word **16.0.17928.20148**, SumatraPDF **3.5.2**. Версии считаны из установленных исполняемых файлов. Переход Word выполнен через контекстное меню «Открыть гиперссылку»; PDF — нажатием текста ссылки.

1. **DOCX: ссылка в папку с кириллицей не открывается.** В контрольном перечне ссылка `Материалы/Annex 13.pdf` вызывает «Не удается открыть указанный файл». Обычная `Annex 12.pdf` из того же DOCX успешно открывается в SumatraPDF после штатного подтверждения Word. Из PDF-перечня ссылка в эту русскую папку работает. Значит, файл существует и открытие PDF на компьютере настроено. Генератор DOCX записывает кириллицу как последовательности `%D0...` в `word/_rels/document.xml.rels`; это наблюдение о реализации, а не доказанная окончательная причина отказа Word.
2. **PDF: `#` в папке обрезает путь при переходе.** Ссылка `Hash #/Annex 13.pdf` в SumatraPDF сообщает, что `.../Hash` не найден. Сложный путь исходного примера `Материалы # 50%/O'Brien & Co/Annex 12%.pdf` аналогично обрезается до `.../Материалы`. Контроли с пробелом, кириллицей и `%` без `#` успешно открываются. В PDF записан относительный GoToR с исходным `/F` и `/UF`; принадлежность причины генератору или совместимости просмотрщика ещё требует проверки. Заявленное поведение в этой среде не достигнуто.

| Контрольный путь | Word DOCX | SumatraPDF, прямой PDF-перечень |
|---|---|---|
| `Annex 12.pdf` | Открыт правильный файл | Открыт правильный файл |
| `Материалы/Annex 13.pdf` | Ошибка открытия | Открыт правильный файл |
| `Percent 50%/Annex 12%.pdf` | Отдельно не проверялся | Открыт правильный файл |
| `Hash #/Annex 13.pdf` | Отдельно не проверялся | Путь обрезан, файл не открыт |
| Сложный путь исходного примера с кириллицей, `#`, `%`, апострофом и амперсандом | Ошибка открытия | Путь обрезан, файл не открыт |

Контрольные DOCX/PDF заново созданы действующими `exhibit.index_documents.docx` и `pdf_document`, без изменения кода и без ручной правки ссылок. Все цели существуют рядом с перечнем. В четырёх контрольных PDF намеренно одинаковое искусственное содержимое; успешный переход различается по открытому имени файла, а не по заголовку внутри страницы. Исходный двухстрочный пример имеет разные документы Annex 12/13.

Для повторения: открыть `output/review-v060-20261029/viewer-controls/Controls.docx` и `Controls.pdf`; нажать строки PLAIN, CYRILLIC, PERCENT, HASH. Исходный сложный пример находится в `output/submission-index-qa/viewer-case/Moved Submission/`. Проверка обеих соседних целей до/после нового переноса не завершена из-за обнаруженных отказов; её нельзя отмечать успешной.

Перед приёмкой: исправить или доказательно разрешить совместимость относительных ссылок, сохранить исходные имена/файлы без скрытого переименования, добавить адресные регрессии и повторить переходы на конечных пакетах. ## Доработка ссылок после независимой проверки

Предыдущий раздел описывает исходный проход. Новые результаты 29 октября:

- DOCX: относительный IRI сохраняет кириллицу, экранирует ASCII-разделители однократно. Имена/байты файлов не меняются. Проверка ZIP теперь отвергает прежний вариант с `%D0...`, даже когда декодированная цель совпадает. Сравнение с сохранённой самим Word ссылкой и реальный переход **ещё не выполнены**; до них исправление не считается принятым.
- PDF: исходные `/F` и `/UF` сохраняются как буквальные имена, включая `#` и `%`; проверка исключает противоречащие им альтернативы. Независимый нативный PDFium читает четыре точных пути, включая вложенную кириллицу, `%`, `#`, апостроф/амперсанд и буквальное `%23`. Это проверка движка, не нажатие в приложении.
- Установленная `libmupdf.dll` SumatraPDF 3.5.2 вызвана в отдельном процессе без запуска просмотрщика. Она возвращает `file://Hash #/Annex 13.pdf#page=1`: исходный `#` неотличим от разделителя назначения. [Код 3.5.2](https://github.com/sumatrapdfreader/sumatrapdf/blob/3.5.2rel/mupdf/source/pdf/pdf-link.c#L185-L233) добавляет фрагмент без экранирования имени; [потребитель ссылки](https://github.com/sumatrapdfreader/sumatrapdf/blob/3.5.2rel/src/EngineMupdf.cpp#L179-L199) использует эту строку. Это согласуется с ранее наблюдавшимся обрезанием.
- В [коде 3.6.1](https://github.com/sumatrapdfreader/sumatrapdf/blob/3.6.1rel/mupdf/source/pdf/pdf-link.c#L1088-L1116) имя экранируется до добавления назначения, а [SumatraPDF декодирует его после отделения фрагмента](https://github.com/sumatrapdfreader/sumatrapdf/blob/3.6.1rel/src/EngineMupdf.cpp#L179-L208). Стабильная версия на официальном сайте — 3.6.1. Это доказательство различия реализации; работа готовой программы 3.6.1 пока не проверена. Её официальный сервер загрузки вернул HTTP 403, файл не получен, программа не запускалась.
- Автоматически: **332 Python / 25 JS**, включая четыре новые регрессии; полный HTTP/Chromium-сценарий со 100 PDF, переносом/историей/восстановлением и нагрузка 500 строк (11,23 с; 14 635 151 байт пика Python; 500 подготовок, временные файлы удалены). Прежние ZIP/источники в проверочных проектах сохраняются. Доказательства: `output/submission-index-links-20261029/source-qa/`, `engine-352.json`.

Окна и ввод пользователя при этой доработке не использовались. Перед реальными переходами требуется отдельное разрешение на короткую проверку. Панель Word и настройки безопасности не меняются. Задачи 3.3/3.5/7.2 пока открыты; черновик релиза не публикуется.

Первый новый CI 40885859623 выявил две ошибки проверочных средств на Mac ARM: PDFium возвращает HFS-разделители `:` ([исходник DecodeFileName](https://github.com/chromium/pdfium/blob/main/core/fpdfdoc/cpdf_filespec.cpp#L28-L43)), а искусственный HTTP-сервер теста остановки не читал POST-тело, вызывая `ConnectionResetError`. Уточнено точное платформенное ожидание PDFium; HTTP-фикстура читает тело и передаёт Content-Length. Приложение ради этих отказов не менялось; простой повтор без исправления не засчитывается.
