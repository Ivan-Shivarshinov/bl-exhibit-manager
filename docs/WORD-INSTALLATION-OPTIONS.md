# Решение по установке панели Word

Исследование 5 октября 2026 для `self-service-onboarding`. Пользователь выбрал вариант B — локальное экспериментальное подключение для пилота; вариант A оставлен как сравнение. Выбор механизма не означает пройденной проверки установщика. Самостоятельное приложение и его документы остаются локальными; панель необязательна.

## Что подтверждает документация

Microsoft разделяет установку для тестирования и распространение пользователям. Network share работает только на Windows и не поддерживается для production-надстроек. Копирование XML в `wef` на Mac — sideload для тестирования. Автоматизация этих операций не меняет назначение механизмов.

Для опубликованной в Marketplace панели Microsoft документирует ссылку `ms-word:...`, открывающую Word с новым документом и устанавливающую панель на Windows/Mac. Пользователь может подтвердить открытие Word и необходимые разрешения; искать XML или каталог не нужно. Фактическую работу панели приложение всё равно должно проверять отдельно.

Источники: [распространение](https://learn.microsoft.com/en-us/office/dev/add-ins/publish/publish), [установочная ссылка и Windows installer](https://learn.microsoft.com/en-us/office/dev/add-ins/publish/publish-office-add-ins-to-appsource), [network share](https://learn.microsoft.com/en-us/office/dev/add-ins/testing/create-a-network-shared-folder-catalog-for-task-pane-and-content-add-ins), [Mac sideload](https://learn.microsoft.com/en-us/office/dev/add-ins/testing/sideload-an-office-add-in-on-mac).

## Вариант A: публичная панель через Marketplace

- Пользовательский путь: запустить приложение → «Подключить панель» → подтвердить открытие Word → получить панель; приложение показывает её ответ. При настройке локального HTTPS подтверждается конкретное изменение доверия.
- Требуется аккаунт издателя Partner Center, подача на проверку Microsoft, публичный HTTPS-хостинг интерфейса панели, страницы поддержки и приватности. Бэкенд проектов не публикуется.
- Нужен отдельный прототип безопасного соединения публичной панели с локальным приложением: явное сопряжение, ограничение разрешённых origin, локальный TLS, отсутствие передачи документов на хостинг. Текущий сервер намеренно отклоняет внешние origin; простое включение CORS для всех недопустимо.
- После публикации используется документированная установочная ссылка для обеих ОС. Windows auto-install через реестр не является общим решением: он также требует Marketplace и более нового build Office (18227 для текущего пользователя); для обеих ОС предпочтительна ссылка.
- Публикация не гарантирована. Текущий локальный XML нельзя просто отправить как готовый: требования магазина включают команды панели и поддержку совместимых клиентов, в том числе Word в браузере и на Mac. Эти сценарии увеличивают согласованный объём.
- Интернет нужен для получения опубликованной панели и загрузки её интерфейса. Домен, хостинг, расходы и аккаунт издателя не выбраны и не создаются автоматически.

Перед реализацией внешней части нужно согласовать расширение объёма; перед публикацией — проверить конкретные файлы, адреса и пользовательский путь.

Источник ограничений: [политики Marketplace, раздел 1120.3](https://learn.microsoft.com/en-us/legal/marketplace/certification-policies#11203-functionality), [манифест и HTTPS](https://learn.microsoft.com/en-us/office/dev/add-ins/develop/add-in-manifests).

## Вариант B: локальная экспериментальная панель

- Сохранить панель в готовом локальном пакете и автоматизировать документированный sideload для ограниченного пилота: приложение готовит технические файлы и собственную регистрацию, пользователь подтверждает доверие и открывает Word.
- Не нужны магазин, tenant и хостинг интерфейса. Загрузка Office.js с CDN Microsoft остаётся существующей внешней зависимостью панели.
- Механизм честно обозначается экспериментальным подключением для пилота; не объявляется поддерживаемым Microsoft способом production-распространения. Ограничения Office и организации сохраняются.
- Реализация должна иметь безопасный повтор и удаление только собственных объектов. На Windows нельзя создавать SMB-ресурс лишь ради обхода ограничения; требуется проверить документированный локальный developer sideload. На Mac используются отдельные платформенные операции.
- Допустимость тестового механизма для пилота явно согласована 5 октября. Прототип установщика и настоящий Word проверяются после такого решения.

## Поддерживаемый Word и доступная проверка

Нужен WordApi 1.5: Windows 2302/build 16130.20332 или совместимая редакция (Microsoft отдельно указывает Office 2024 для LTSC), Mac 16.70 или новее. Это доступность API, а не доказательство установки и работы всего приложения на каждом build. Тип лицензии не используется как запрет. [Таблица Microsoft](https://learn.microsoft.com/en-us/javascript/api/requirement-sets/word/word-api-requirement-sets).

Доступный CI выполняет нативную сборку на виртуальных Windows 2022, macOS 15 Intel и ARM. Он проверяет пакеты, HTTP/HTTPS, обработку документов, повторный запуск и обмен архивами. Протокол присутствия панели проверяется отдельно с явно имитированным Word host. Workflow устанавливает LibreOffice; установка и активация Word в нём не настроены, self-hosted runners у репозитория отсутствуют. Проверку Office.js в настоящем Word нельзя вывести из успешной конвертации LibreOffice или браузерной имитации.

Выбранный вариант B сохраняет обычный путь DOCX/PDF без настройки панели. Регистрация Windows повторяет целевую запись официального `office-addin-dev-settings`, без включения отладчика; Mac использует собственный файл в `wef`. Учебный DOCX для открытия панели создаётся приложением, по модели sideload-документа Microsoft. Задачи реализации и проверки закрываются по доказательствам, отдельно от выбора варианта.
